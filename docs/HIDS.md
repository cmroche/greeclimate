# Known HIDs

Gree's `hid` identifies a firmware target and build, not an appliance serial number. The app uses its numeric firmware code to check for updates ([update sequence][update-sequence]). The historical catalog below records public reports and named firmware files researched on 2026-10-14, not upgrade compatibility. Neither a filename nor a firmware string proves what an installed appliance reports. Detailed payload inventories and analysis are preserved in [private gree-research](https://github.com/cmroche/gree-research/blob/main/docs/HIDS.md); using this library does not require that checkout.

## String segments

Example: `362001066763+U-W06A(P3)V6.04.bin`, reported for Sinclair air-to-water units with MID `9300`:

| Segment | Meaning and limits |
| --- | --- |
| <a id="362001066763"></a><code>362001066763</code> | opaque firmware code, sent as <code>firmwareCode</code> to Gree's update API. Code lengths vary; no subfield decoding is verified. |
| <code>+</code> | separates the code from the firmware name; it is not part of the filename prefix. |
| <code>U-</code> | literal prefix with no verified expansion; some names omit it. |
| <code>W06A</code> | [INFERENCE] module/platform designation; individual characters are not decoded. <code>CS532AE(LT)</code> is independently documented as a Wi-Fi module name ([certification][module-certification]). |
| <code>(P3)</code> | [INFERENCE] variant qualifier, not proof of protocol version 3. Its expansion is unknown; <code>LT</code>, <code>MTK</code>, and <code>MTK2</code> need not mean the same thing. |
| <code>V6.04</code> | literal firmware-version string. Gree's separate <code>commProtVer</code> field is the communication protocol version. Do not compare versions across firmware families. |
| <code>.bin</code> | image-filename extension, not proof of executable content or a reported HID. |

The device's [`version`](../greeclimate/device.py) extracts the terminal `V<digits/dots>.bin` suffix for display only. The [trait matcher](../greeclimate/device_profile.py) matches the exact string before the first `+`, or a bare firmware code. It does not validate or constrain the suffix, module, qualifier or version: even `362001065634+incomplete` selects that code's traits. Missing, nonstring and unknown-code inputs return no profile; codes are not trimmed or normalized.

### Firmware-code traits and limitations

`DeviceProfile(firmware_code, temperature_offset=None, relearn_temperature_offset=False, buzzer_properties=None)` and `match_device_profile(hid)` are direct-submodule APIs. Each code has one consolidated record. Exact-HID overrides and version floors are removed without aliases. This deliberately broadens buzzer matching from inspected builds to every suffix and revision of the same code, including uninspected builds. The registry selects temperature and buzzer traits only: it does not infer an appliance family, add a capability API, or establish protocol support.

When migrating older constructors, use keyword arguments for optional traits rather than reusing the old positional `min_version`/relearning argument list. For example: `DeviceProfile("362001064973", temperature_offset=40, relearn_temperature_offset=True, buzzer_properties=("Buzzer_ON_OFF",))`.

For valid ambient readings, Celsius is network `TemSen` minus the client offset. A normalized firmware response must not have 40 subtracted twice. Defaults of 0 or 40 extrapolate inspected sensor paths to the whole code; they are not physical calibration of every mainboard or revision. The fallback identity `362001000968` now has offset 0 and `362001063525` has offset 40, as code-scoped policy rather than proof that every reported use has the same sensor path. Unknown or temperature-unspecified profiles retain automatic detection, not an assumed zero offset. MID, module, display units and setpoints do not identify the encoding.

Automatic detection assumes indoor temperatures from −20°C through 50°C. Incoming nonzero integer samples in the supported range learn an offset only when the plain and offset-40 interpretations are unambiguous; ambiguous samples retain the first guess. Learned offsets take precedence over defaults. Codes `362001061381`, `362001061383`, `362001062557`, `362001064270` and `362001064973` continuously re-learn because runtime configuration or cached samples can change encoding: samples 1…39 select 0, 51…90 select 40, and 40…50 remain ambiguous. Their default 40 is provisional, and an earlier guess survives HID arrival. Zero does not teach an offset; malformed/out-of-range samples do not change inference. HID-only updates refresh the selected traits without learning or resetting calibration. No safe LAN query advertising an offset was established; do not probe unknown names or write controls on live hardware to infer calibration.

Buzzer namespaces are also code-scoped. `buzzer_properties=None` means unestablished; `()` is an explicit exclusion. `362001065634` retains commercial `Buzzer_ON_OFF` support across revisions, while `362001066763` retains only an explicit buzzer exclusion, not air-to-water controls. With local `Device.buzzer=False`, supported `Buzzer_ON_OFF` adds value 1 to each command; enabling it adds no such field. A `BuzzerCtrl` namespace, if declared, sends the local boolean value. Recognized names and native storage do not establish physical acoustic behavior, hardware boot defaults or mute polarity; the command values preserve the existing client convention. Shared MIDs do not imply shared buzzer namespaces.

MID is separate discovery metadata, not an HID segment; see [MIDS.md](MIDS.md). An HID or CPU target does not prove appliance model, protocol support, capabilities, or safe replacement firmware.

Detailed inspected-build provenance is retained in [private temperature/buzzer research](https://github.com/cmroche/gree-research/blob/main/docs/OFFSETS.md); [public regressions](../tests/test_device_profile.py) cover the code-scoped client policy. No current profile enables `BuzzerCtrl`.
