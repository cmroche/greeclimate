# Known MIDs

A MID is reported in discovery metadata (`mid`) or a gateway's `subList` entries. Preserve it as a string, including letters; it is separate from the firmware identifier (`hid`), documented in [HIDS.md](HIDS.md). See [GATEWAYS.md](GATEWAYS.md) for multi-unit discovery and addressing.

## Historical polling catalog

These polling lists are not a universal firmware capability or temperature-encoding contract. A field omitted from an app's default poll can still have an explicit-query handler; an unsupported query can return a generic zero instead of a sensor value. The firmware-routing evidence below is separate from observed device MIDs and must not be used to infer an appliance model from a string embedded in a binary.

## Gateway observations and sources

- [PR #148's hardware log](https://github.com/cmroche/greeclimate/pull/148#issuecomment-6173155943) reports a GR-Gcloud gateway with MID `60`, three indoor units with MID `608f`, and one with MID `605c`. A separate standalone air conditioner reports MID `10001`. The log establishes these associations, not the indoor units' retail models or supported polling fields.
- [Issue #101](https://github.com/cmroche/greeclimate/issues/101) reports a MID `60` gateway advertising six indoor units; the returned five-entry list contains MIDs `6049`, `6092`, and `604c`.
- PR #148 links to HACS integration PR #508: [W06 packet notes](https://github.com/RobHofmann/HomeAssistant-GreeClimateComponent/pull/508#issuecomment-5795667844) associate MID `60` with `362001067012+U-W06AV30.bin` and show indoor MIDs `608f` and `6092`. [An older four-unit capture](https://github.com/RobHofmann/HomeAssistant-GreeClimateComponent/pull/508#issuecomment-5795708142) shows indoor MID `604b`, without establishing its gateway HID.
- A gateway's HID identifies the gateway firmware, not necessarily the firmware of each indoor unit. Enumeration alone does not establish a child's supported status fields, and synthetic test fixtures are not additional hardware observations.

## Firmware MID evidence

The expanded download survey adds **compiled routing IDs, default/fallback IDs, and explicitly emitted IDs**, not new observations of installed appliances. The role and condition in each row matter: a list of child routes is not the gateway's own MID, and a fallback is not an unconditional emitted value. Identifier spelling/case is preserved from the inspected branch or table.

The rows below link exact downloaded SHA-256 payloads in [HIDS.md](HIDS.md#downloaded-payload-inventory). They include only positively recovered fixed identifiers; an omitted payload or empty fixed-ID list does not establish that the firmware lacks a MID. Some modules construct their MID from runtime mainboard data. Firmware routing does not establish a retail appliance model or a universal polling-field list.

**MID does not determine the temperature offset.** MID `9300` occurs in the ATW family with `EnvironmentTem`, in an ESP32 test build whose finite status interface lacks `TemSen`, and as metadata in opaque WB06 MCU bridges whose ambient conversion remains unresolved. A common `10001` default likewise does not establish a measured TemSen path. Gateway MID `60` is distinct from child identifiers; an allowed child route alone does not calibrate `TemBody`, `TemSor`, or `TemSen`. The [Wi-Fi protocol follow-up](../OFFSETS.md#wi-fi-protocol-indicators) also distinguishes sample encoding from unit flags and the current platform selector.

For ZTS31A `362001068423` V3.09/V3.10, the recovered offset-40 result is limited to particular UART plugins: `13806 → lib13806.so`, `13807 → lib13807.so`, `11012/11002/10014 → lib11012.so`, `11000 → lib11000.so`, and `10f05 → lib10f05.so`. The larger plugin-routing list is **not** an offset-40 allowlist. See [OFFSETS.md](../OFFSETS.md#gateway-and-incomplete-response-limits) for scope and calibration limits.
